## 슬라이드 1 — 계층 구조 (모듈 관계)

**단방향 의존 — 상위는 하위를 알고, 하위는 상위를 모른다**

```
[UI 계층]     TabManager · TabView · 13개 탭
    ↑ (측정 방송 broadcast)
[엔진 계층]    CaptureController · MeasurementEngine
    ↑
[DSP 계층]     tg_process (검출 계산)
    ↑
[캡처 계층]    Audio · Playback · Sim 워커 (별도 스레드)
```

| 속성 | 내용 |
|---|---|
| 의존 방향 | 항상 상위→하위 단방향, 순환 없음 |
| 결합도 | 계층 간은 모델(스냅샷·WaveBlock)로만 연결 |
| 스레드 경계 | 캡처=별도 스레드 → 큐로 메인에 전달 |

## 슬라이드 2 — TabView 패턴 · 전술

| 패턴 / 전술 | 적용 위치 | 효과 |
|---|---|---|
| **Split Module 전술** (QA-MOD-01) | 탭 = 자기완결 모듈 | 화면 추가/수정 격리 |
| **추상 기반 인터페이스** | `TabView` 공통 계약 | 코어가 구체 탭에 비의존 |
| **Template Method** | 베이스: `showEvent→onShown`·`frameDue` / 탭: `onMeasurement`·`onWave` override | 공통 뼈대 재사용, 차이만 구현 |
| **Observer (Publish-Subscribe)** | `broadcastMeasurement` → 전 탭 `onMeasurement` | 코어 송출, 탭 각자 갱신 |
| **Plugin 등록** | `registerTab` 한 줄 | 새 탭 = 클래스1 + 등록1줄 |

> 결과: 새 탭 추가·수정에도 **기존 화면·계산부 무수정** (개방-폐쇄)

## 슬라이드 4 — 계측 결과

**PERF 계측 (파이, 블록 처리 예산 = 19ms)**

> **"블록"이란?** 오디오 입력을 처리 단위로 자른 한 조각(≈960 샘플 ≈ 19ms 분량).
> 다음 블록이 도착하기 전(19ms 안)에 계산+렌더를 끝내야 실시간 유지 → **예산 = 19ms**

| 단계 | 실측 (avg / max) | 예산 대비 |
|---|---|---|
| DSP 계산 (`tg_process`) | 0.47 / 0.55 ms | **2.5%** |
| 화면 그리기 (페인트) | 8.6 / 24.8 ms | **45%** |
| 처리 밀림 (backlog) | ≈1블록 | 실시간 유지 |

> 병목은 **DSP가 아니라 렌더링(페인트)** — 계산의 약 18배
> → 개선은 모두 렌더링 경로에 한정, 계산부는 미변경

---

## 슬라이드 5 — 개선 ① 안티앨리어싱(AA) 비활성

**AA란?** 선·도형의 경계에 생기는 계단 모양(aliasing)을 줄이려고,
경계 픽셀을 주변 색과 반투명하게 섞어 부드럽게 보이게 하는 렌더링 기법

- **비용:** 픽셀마다 경계 계산 + 알파 블렌딩. 선·점이 많은 그래프를
  CPU(소프트웨어)로 그릴 때 비용이 큼
- **판단:** 실시간 그래프는 초당 수십 회 갱신 + 선이 촘촘 →
  AA 유무가 **육안으로 거의 구분 안 됨**
- **적용:** `setNotAntialiasedElements(aeFills|aePlottables|aeScatters|aeItems)`
  — 채움·플롯·산점·아이템의 AA만 끔 (축·텍스트는 유지)
- **효과:** 단일 개선 중 최대 — **페인트 시간 약 −57%**

---

## 슬라이드 6 — 개선 ② 데시메이션 (다운샘플)

**데시메이션이란?** 화면이 표시할 수 있는 것보다 데이터점이 훨씬 많을 때,
**가로 픽셀 폭에 맞춰 대표값만 남기고 점을 줄이는 것**

- **왜 필요한가:** 가로 픽셀이 그래프의 표시 한계 — 한 픽셀 열에는
  **한 점만 찍힘.** 데이터점 수만~수십만은 **여러 개가 같은 픽셀 열에 몰림** →
  다 그리면 **같은 픽셀에 반복 덧그리기**(화면은 동일, 비용만 낭비)
- **가변 기준:** 픽셀 폭은 고정이 아니라 **현재 플롯 폭에 연동** —
  창을 리사이즈하면 데시메이션 목표점 수도 함께 바뀜
- **방법:** 각 픽셀 열 구간에서 **min/max(위·아래 극단)** 만 추출 →
  픽셀당 ~2점으로 축소
- **왜 min/max?** 단순 평균/솎기는 파형의 피크를 놓쳐 뭉개짐.
  min/max는 파형 외곽선을 보존 → **정보 손실 최소**
- **효과:** 정점 수가 데이터 양과 무관하게 **화면 폭에 바운드** →
  페인트가 데이터 크기에 비례해 늘지 않음

---

## 슬라이드 7 — 개선 ③ 프레임 코얼레스 (30fps 상한)

**코얼레스란?** 짧은 시간에 그리기 요청이 몰릴 때, 디스플레이가 실제
갱신 가능한 간격(33ms) 안의 요청을 **하나로 합쳐 한 번만 그리는 것**

- **문제:** 오디오는 작은 청크로 자주 들어옴. 백로그 처리 시 한 번의
  입력 처리에서 `onWave`가 여러 번 호출 → 매번 배열 재빌드 + 렌더 중복
- **방법:** `frameDue(33ms)` — 마지막 렌더 후 33ms 미경과면 스킵.
  정상 실시간(간격 ≫ 33ms)엔 영향 없고 **버스트에서만 합쳐짐**
- **33ms의 출처:** 임의값 아님 — **1초 ÷ 30 ≈ 33ms**, 즉 아래 30fps 상한에서 파생

**왜 30fps인가 (근거)**
| 후보 | 페인트 부하 (8.6ms 기준) | 판단 |
|---|---|---|
| 60fps (16.6ms) | 60×8.6 ≈ **코어 51%** | 과다 |
| **30fps (33ms)** | 30×8.6 ≈ **코어 26%** | **채택** |
| 15fps 이하 | 부하는 낮음 | 추세가 끊겨 보임 |

> 30fps = **부드러운 인지 하한(~24fps) 이상**이면서 60fps 대비
> **페인트 부하를 절반**으로 바운드하는 지점 (측정 paint_fps 26.2와 일치)

## 슬라이드 8 — 결정: DSP 스레드 분리 기각 (ADR)

**가정:** DSP를 별도 스레드로 분리하면 병렬화로 개선

**계측:** DSP는 예산의 2.5%(0.47ms) → 병목 아님

| | 분리 (기각) | 유지 (채택) |
|---|---|---|
| 병목(페인트) 개선 | 없음 | 렌더링 최적화로 해결 |
| 확보 시간 | +0.47ms | — |
| 복잡도 | 락·큐·경쟁상태 증가 | 단일 스레드 단순성 유지 |

> 큰 복잡도 대비 확보 이득 0.47ms → **비용 대비 효과 없음**

## 슬라이드 9 — 결과 및 재검토 조건

**결과 (파이)**
- 실시간 처리에 **CPU 코어 1개의 약 28%** 사용 (72% 여유)

**재검토 조건 (ADR 재개)**
- `dsp_total`이 예산의 20%(≈4ms) 초과

## 슬라이드 10 — 샘플레이트 확장성 (48kHz vs 192kHz)

**같은 파이에서 샘플레이트만 4배로 올려 재측정 (블록당 960 → 3,840 샘플)**

| 항목 | 48kHz | 192kHz | 변화 |
|---|---|---|---|
| DSP (dsp_total) | 0.47 ms | 0.55 ms | **+17% (거의 안 늚)** |
| — 그중 detect | 0.453 ms | 0.485 ms | +7% |
| 페인트 (disp_paint) | 8.6 ms | 7.5 ms | **무증가** |
| backlog | ≈1블록 | ≈1블록 | 실시간 유지 |
| 처리량 fg_sps / spf | 50k / 960 | 201k / 3,840 | ×4 (정상) |

**왜 CPU·화면이 4배 안 늘었나**
- **detect = tic/toc 이벤트(시간) 기준** → 샘플레이트와 무관 (샘플 스캔분 +7%만 증가)
- **페인트 = 데시메이션**이 점 수를 픽셀 폭에 고정 → 샘플레이트와 무관

**메모리·발열 (여기가 유일한 실질 제약)**
| 항목 | 48kHz | 192kHz | 배수 |
|---|---|---|---|
| PSS (절대 플래토) | 392 MB | 1,069 MB | ×2.7 |
| RSS (물리 총량) | 441 MB | 1,119 MB | ×2.5 |
| 이력버퍼 할당 계단 | +213 MB | +825 MB | ×~4 |
| 온도 피크 | 75.2 °C | 80.7 °C | +5.5 °C |
| 스로틀 | 없음 | 없음 | — |

> ※ 메모리 수치는 **절대 사용량**(증가량 아님). 시작 33MB 대비 총 증가 = **+359MB / +1,036MB**.
> 8분 이력 버퍼가 샘플레이트에 **정비례** → **RSS 1.1GB. 2GB 이하 파이면 이력 버퍼 축소 필요.**

**결론**: 연산·렌더링은 192kHz도 거뜬(누수 없음, 실시간 유지). **유일한 실질 제약은 메모리(1.1GB)와 발열(80.7°C).**

## 슬라이드 11 — End-to-End Latency (측정 구간 · 단계별 시간)

**전체 파이프라인 ① → ⑩ 중, 앱이 잴 수 있는 구간은 ④ → ⑧ 뿐**

```
[앱 밖 · 측정 불가]                 [★ 측정 가능 = 우리의 e2e ★]                  [앱 밖 · 측정 불가]
① 소리 → ② 마이크·ADC → ③ OS버퍼 →│ ④ 링버퍼쓰기 ─cap2proc→ ⑤ 처리시작 ─proc2disp→ ⑦ replot요청 ─disp_paint→ ⑧ 페인트 │→ ⑨ 모니터발광 → ⑩ 눈
                                   │  ★T_capture           ★T_procStart          ★T_replotReq         ★T_paint       │
                                   │  └───────────── e2e_full = cap2proc + proc2disp + disp_paint ────────────┘       │
```

**단계별 시간 (avg) — 전체 파이프라인**
| # / 구간 | 단계 | 측정 | 48kHz | 192kHz |
|---|---|---|---|---|
| ① | 시계 소리 발생 (음향) | ✗ 앱 밖 | — | — |
| ② | 마이크 → ADC (HW) | ✗ 앱 밖 | — | — |
| ③ | OS 오디오 버퍼 (드라이버) | ✗ 앱 밖 | — | — |
| ④→⑤ | cap2proc (링버퍼 큐 대기) | △ Live 전용 | *Sim: 없음* | *Sim: 없음* |
| ⑤→⑦ | proc2disp (DSP+broadcast+빌드) | ✓ | 1.0 ms | 1.76 ms |
| ⑥ | └ 그중 DSP (tg_process) | ✓ | 0.47 ms | 0.55 ms |
| ⑦→⑧ | disp_paint (Qt큐+rasterize) | ✓ | 8.6 ms | 7.5 ms |
| ⑨ | 모니터 발광 (HW) | ✗ 앱 밖 | — | — |
| ⑩ | 사람 눈 | ✗ 앱 밖 | — | — |
| **⑤→⑧** | **측정된 합 (처리→페인트)** | ✓ | **~9.6 ms** | **~9.3 ms** |
| **④→⑧** | **e2e_full (진짜 종단간)** | Live 필요 | *Live 필요* | *Live 필요* |

**측정 가능 구간 = ④→⑧** (앞단 ①②③, 뒷단 ⑨⑩은 앱이 타임스탬프를 못 찍어 측정 불가).

> ⚠️ **cap2proc·e2e_full은 Live 캡처 전용 계측**입니다. 이번 48k·192k는 **Sim 실행**이라 그 값이 없어,
> "처리→페인트"(⑤→⑧) 구간만 측정됩니다(**≈9.3–9.6ms, 샘플레이트 무관**).
> 캡처를 포함한 진짜 종단간이 필요하면 **Live 모드로 재측정**해야 합니다.

**예산 대비 (측정 가능 구간 ⑤→⑧)**
| | 48kHz | 192kHz |
|---|---|---|
| 필요 시간 (블록 마감 = 예산) | 20 ms | 20 ms |
| **지금 처리(처리→페인트 합)** | **9.6 ms** | **9.3 ms** |
| **남는 여유** | **≈10.4 ms (52%)** | **≈10.7 ms (54%)** |

> ※ 페인트(8.6/7.5ms)는 **30fps로 별도 제한** → 매 블록엔 없음. 페인트 없는 일반 블록은 **proc2disp만(1.0/1.76ms)** 사용(여유 ~19/18ms).
> 9.6ms는 "블록 처리 + 페인트가 겹친 최악 블록" 기준. backlog ≈1블록 유지로 실시간 확인.
