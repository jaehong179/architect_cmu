# 데이터 경로 · 버퍼링 · 과부하 거동 (Live Render Path & Buffering)

> 신호 입력부터 화면 렌더링까지의 경로, 버퍼 구조(왜 탭별로 나누고 왜 8분인지), 렌더 타이밍, 그리고 `processSamples`가 하드웨어 한계로 느려질 때의 거동을 정리한 문서.
> 모든 수치·식별자는 코드 기준. (`src/engine/CaptureController.cpp`, `src/audio/*`, `src/ui/tabs/*`)

---

## 0. 한눈에 — 세 개의 버퍼

이 시스템에는 성격이 다른 버퍼가 **세 종류** 있다. 섞어서 보면 헷갈린다.

| 버퍼 | 위치 | 크기 | 역할 | 식별자 |
|---|---|---|---|---|
| **입력 캡처 링** | 워커 ↔ 메인 스레드 사이 | **30초** | `processSamples`가 읽어가는 원본 PCM | `p->Samples` (`SECONDS_OF_BUFFER 30`) |
| **탭 라이브 버퍼** | 각 탭 내부 | **0.5 ~ 2.2초** | 라이브 렌더용 작업 버퍼(보이는 창) | `WaveBuffer mBuf` (탭별) |
| **중앙 이력 버퍼** | 비시각 sink 1개 | **8분(480초)** | 정지·스크롤백·seek 전용 이력 | `WaveLodHistory` |

핵심: **입력 링(30초)** 은 스레드 간 전달용, **탭 버퍼(짧음)** 는 라이브 그리기용, **이력(8분)** 은 과거 되감기용. 서로 다른 목적이다.

## 1. 단위 정의 (sample → block → beat → window → history)

```
샘플(sample)     1개. 절대 인덱스 = 전역 시간좌표
   │              (startSample, mInputAbsSample += slice 로 매김)
블록(block/slice) ≤ 4096 샘플 (DETECTOR_NUMBER_OF_SAMPLES)
   │              = tg_process 1회 입력 = broadcastWave 1회 = onWave 1회
   │              48kHz → ≈85ms,  192kHz → ≈21ms
비트(beat)        sr×3600/bph 샘플.  예) 28800bph@48k = 6000샘플 ≈125ms
   │              → 블록(85ms) < 비트 1개
보이는 창(window) 탭별 0.8~2.2초 = 수십 블록
   │              예) 2.2초@48k ÷ 85ms ≈ 26블록
이력(history)    8분 = ~5,600블록@48k
```

> 한 블록(≤4096)은 비트 한 개도 다 못 채운다. 그래서 한 화면(수십 블록)을 그리려면 **누적 버퍼가 반드시 필요**하다.

## 2. 신호 → 렌더 전체 시퀀스

```
[워커 스레드]                          [메인(GUI) 스레드]
 TAudioWorker/Playback/Sim
   │ 캡처 → p->Samples(30초 링)에 기록
   │ (WriteIndex / TotalSamplesWritten 증가, Mutex)
   └─ emit *DataReady ───(Qt queued)──▶ CaptureController::onAudioData
                                            │ 상태 스냅샷(Mutex) → unlock
                                            │ processSamples(p)
                                            ▼
                          ┌─ processSamples (슬라이스 루프) ─────────────┐
                          │ backlog = TotalSamplesWritten - lastDone     │
                          │ while(backlog>0):                            │
                          │   slice = min(backlog, 4096)                 │
                          │   링 → mInputBlock 복사 (읽기인덱스 전진)    │
                          │   tg_process(mInputBlock, slice, &r)         │ ← DSP: 정류·평활→엔벨로프, A/C검출, sync/bph
                          │   WaveBlock wb{env, raw, events,             │
                          │     startSample(절대), sr, bph, ...}         │
                          │   mTabs->broadcastWave(wb)                   │
                          │   mInputAbsSample += slice                   │
                          └───────────────────┬──────────────────────────┘
                                              ▼
                          ┌─ TabManager::broadcastWave ──────────────────┐
                          │ if(!paused) 각 탭 → onWave(wb)               │ ← 라이브(정지 시 동결)
                          │ 항상 각 WaveSink → onWave(wb)                │ ← WaveLodHistory(8분, 정지 무관 누적)
                          └───────────────────┬──────────────────────────┘
                                              ▼
                          ┌─ Tab::onWave(w) ─────────────────────────────┐
                          │ mBuf.push(w)   // 끝 85ms 조각 추가          │ ← mBuf[a % mCap], 이벤트 append/trim
                          │ (탭별 처리: processNewBeats 등)              │
                          │ if(isVisible()) render()                     │ ← 숨은 탭은 누적만
                          └───────────────────┬──────────────────────────┘
                                              ▼
                          ┌─ Tab::render() ──────────────────────────────┐
                          │ 최신 윈도우 [from, from+count) 를 mBuf 에서  │ ← w 가 아니라 "버퍼"를 그림
                          │ scopePlotWindow → copyRange (없으면 0패딩)   │
                          │ graph->setData(x=시간, y=env)                │
                          │ replot(rpQueuedReplot)                       │ ← 실제 paint 는 이벤트루프에서 병합 실행
                          └──────────────────────────────────────────────┘
```

스레드 경계: **캡처는 워커 스레드, DSP·방송·버퍼·렌더는 전부 메인(GUI) 스레드.** 둘을 잇는 게 30초 입력 링 + 절대 샘플 카운터.

### 슬라이스 루프 — "한 링을 4096씩 걸어가며 따라잡기"
- `tg_process` 1회 = 무조건 ≤4096 (한 조각). `mInputBlock`이 4096 크기 임시 그릇.
- 그러나 `processSamples` 1회는 `while(backlog>0)`로 **여러 조각을 연속** 처리해 backlog를 0까지 비운다.
- 4조각이라 해도 **데이터 출처는 1개(30초 링)**. `mInputBlock`을 재사용해 링의 다음 4096을 떠올 뿐, 다른 버퍼가 아니다.

## 3. 렌더 타이밍 — 데이터 구동 + 슬라이딩 윈도우

- 렌더는 **별도 타이머가 아니라 블록 도착(onWave)마다** 호출된다. → 렌더율(FPS) ≈ 블록 빈도 (48k→~12, 192k→~47), 숨은 탭은 0(`isVisible()` 가드).
- **render는 들어온 블록 `w`가 아니라 누적된 `mBuf`를 그린다.** 새 블록은 창의 끝 85ms만 보태고, 나머지는 이전 블록들이 채워둔 상태.
- 시작 직후 창이 덜 찼을 땐 `copyRange()`가 빈 구간을 **0으로 패딩**해 깨지지 않고 왼쪽부터 차오른다. ~10블록(≈0.8초) 뒤부터 매 프레임 완전.
- 절대 인덱스 주소화(`a % mCap`)라 블록 순서/누락에도 각 샘플이 제 위치에 꽂혀 정합 유지.

> "onWave에 화면 전체 값이 보장되는가?" → **보장 안 됨. 그래서 버퍼가 누적해 보장한다.**

## 4. 왜 탭별로 분리했나 + 왜 8분인가 (ADR-004 핵심)

### 4.1 왜 8분
8분은 임의값이 아니라 **시계 측정 워크플로**에서 유도된다.

- 자세 변경 후 측정이 신뢰 가능해지기까지: 헤어스프링 안정화 ≈ **15초** + 이스케이프휠 1회전 ≈ **60초** = **자세당 ≈75초**
- 표준 **6자세**(문자판 위/아래, 용두 위/아래/좌/우): 75 × 6 = **450초 (7.5분)**
- 여유 올림 → **480초 = 8분**

→ 8분 = "6자세 한 사이클 전체를 항상 담아 어느 자세든 스크롤백 가능한 최소 길이 + 여유".

### 4.2 왜 탭별 분리 (2단 구조)
"긴 이력은 중앙 하나 / 짧은 라이브는 탭마다"로 역할을 나눈다. 한쪽으로 몰면 둘 다 깨진다.

- **탭마다 8분을 들면?** → 8분 풀해상도 1벌 ≈ **210MB** × 탭 수 = **수 GB** (같은 데이터 중복). ❌
  → 8분은 **중앙 `WaveLodHistory` 하나로 통합**. → RISK-03 완화, QAS-03(장시간 자원 안정성) 충족.
- **라이브도 중앙에서 매 프레임 가져가면?** → N개 탭 × 매 프레임 재조립 = 핫패스에 일이 N배. ❌
  → 종단간 지연(QAS-02)·타이밍 정밀도(RISK-18) 위협.
  → **라이브는 탭마다 자기 짧은 버퍼(0.5~2.2초)에서 직접** 렌더. 탭 버퍼 합쳐도 ~3.4MB(48k).
- **게다가 탭마다 필요 형태가 다름**: 길이(0.8 vs 2.2초)·형태(env만/raw만/둘 다/폴딩/필터)가 달라 짧은 버퍼는 탭마다 두는 게 자연스럽다.

```
                    ┌─────────── 중앙 1개 ───────────┐
broadcastWave ─┬──▶ │ WaveLodHistory (8분 = 6자세)    │ ← 긴 이력: 중복 방지 위해 하나
               │    │ pause·스크롤백·seek 전용        │
               │    └──────────┬─────────────────────┘
               │               │ seek 시에만 replay 로 끌어옴
               │               ▼
               └──▶ 탭1 WaveBuffer(0.8s) ─ render  ← 라이브: 직접·매프레임·싸게
                    탭2 WaveBuffer(1.6s) ─ render     (탭별 길이·형태 상이)
                    탭3 WaveBuffer(2.2s) ─ render
```

| | 길이 | 개수 | 이유 |
|---|---|---|---|
| 중앙 이력 | 8분 | 1개 | 6자세 사이클 보존 + 탭마다 들면 GB 폭발 → 통합 |
| 탭 라이브 버퍼 | 0.5~2.2초 | 탭마다 | 라이브를 매 프레임 싸게 직접 렌더 + 탭별 형태/길이 상이 |

> seek(가끔) ↔ 라이브(매 프레임), 메모리 ↔ CPU 를 각각 싼 쪽으로 가른 결과. 가끔 일어나는 seek 에는 이력에서 한 번 끌어와 탭 버퍼에 채우고(`replayInto`), 매 프레임 라이브는 탭 버퍼에서 직접 그린다.

## 5. 과부하 거동 — `processSamples`가 하드웨어 한계로 느려지면

워커(캡처)는 별도 스레드라 소비자가 느려도 **계속 30초 링에 쓴다.** 이 비대칭이 아래를 만든다.

### 1단계 — 백로그 누적 (정상 흡수)
- `processSamples`가 한 번 오래 걸리면 그동안 워커가 더 써서 다음 호출의 `backlog`가 커진다.
- `while(backlog>0)` 루프가 4096씩 끝까지 드레인해 **따라잡는다**.
- **일시 스파이크면 자가 회복**: 보통 4096 처리(수 ms) ≪ 블록 생성시간(85ms@48k)이라 한 콜에서 밀린 걸 다 빨아들이고 실시간 복귀.
- 예) 300ms 멈춤 → 14,400샘플 밀림 → 다음 콜에서 4096×3+2112 = 4조각 ≈20ms에 드레인 → 복귀.

### 2단계 — GUI 프리징 (지연이 길면)
- `processSamples`는 **GUI 스레드**라, 길게 잡으면 **Qt 이벤트 루프가 막힌다** → 화면 repaint 지연(멈췄다 버스트), 입력 렉.
- 백로그가 크면 슬라이스마다 `render()`가 반복 호출됨. `rpQueuedReplot`이 페인트는 1번으로 병합하나 `copyRange`+`setData`는 N번 → **헛수고 CPU**.

### 3단계 — 입력 링 오버런 (지속적으로 못 따라가면) ← 가장 위험
- 처리속도 < 입력속도가 **지속**되면 backlog가 **30초(=링 용량) 초과**.
- `AudioRingBuffer::write`는 **소비자 미소비분 덮어쓰기를 검사하지 않는다** (그냥 `% N` 랩, "rollover" 로그는 정상 랩이라 매번 찍힘).
- 오버런 시: 리더는 `mInputAbsSample`로 절대좌표를 독립적으로 매기는데 슬롯 내용은 이미 더 새 데이터로 덮임 → **내용↔좌표 desync, 순서 꼬임** → 검출기 `sync_lost`/`detector_reset` → 파형 깨짐·레이트 튐. 크래시는 없지만 측정 신뢰 붕괴.

### "30초면 무조건 안전"이 아닌 이유 (두 조건)
- **① 손실 없음**: backlog가 30초 미만이면 오버런 없음. (필요조건)
- **② 실시간성**: 그것만으론 부족. backlog가 **0으로 다시 빠져야**(= 처리 ≥ 입력) 한다. 15초쯤에 눌러앉으면 손실은 없어도 **화면이 항상 15초 지연**된 과거 → 실시간성 위반(QAS-02).
- **30초 링 = 일시 충격 흡수기**이지, 계속 느려도 되는 면허가 아니다. 지속 지연이면 ②(지연 누적)를 거쳐 ③(오버런)으로 간다.

```
backlog
30s ┤- - - - - - - - - - - - - 넘으면 → 오버런(손실)
    │        ╱╲                ① 스파이크 후 0복귀 = 진짜 OK
15s ┤   ╱╲ ╱  ╲___   ┌───────  ② 15s 눌러앉음 = 손실X but 항상 15s 지연 = 문제
    │__╱  ╲╱      ╲__╱
 0s ┤______________________________▶ 시간
```

### 보호되는 것 / 안 되는 것
| 항목 | 상태 |
|---|---|
| 30초 헤드룸 (일시 스파이크 흡수) | ✅ |
| 백로그 catch-up 루프 (일시 지연 회복) | ✅ |
| 숨은 탭 render 스킵 (`isVisible()`) | ✅ |
| backlog/latency 계측 (PERF A-2) | ✅ 관측 가능 |
| **소비자(읽기) 오버런 감지** | ❌ 덮어쓰기 검사 없음 (무음 오버런) |
| catch-up 중 중복 render | ❌ 슬라이스마다 그림(낭비) |
| `DroppedSampleEstimate` | ⚠️ **캡처측 드롭만** 잡음(`expected−written`), **소비자 오버런은 못 잡음** = 사각지대 |

> 관련 리스크/품질: RISK-08(피크 부하 미정의 → 비정상 동작), RISK-02(지연 초과), RISK-03(렌더 확장성), QAS-02/QAS-03.

## 6. 성능 계측(PERF) 메트릭

`processSamples` 처리 시간을 보려면 **`proc2disp_latency_ms`** (태그 `A-2` / `QA-LT-01`).
`perfDispMs − perfProcStartMs` = 백로그 전체를 4096씩 다 처리(+setData)하는 데 걸린 시간.

| 메트릭 | 구간 | 의미 |
|---|---|---|
| `backlog_samples` | — | 처리 직전 밀린 샘플 수 |
| `cap2proc_latency_ms` | 캡처 → 처리 시작 | 처리 **전** 대기(지연) |
| **`proc2disp_latency_ms`** | **처리 시작 → 표시 요청** | **processSamples 처리 시간** |
| `disp_paint_ms` | 표시 요청 → 실제 페인트 | QCustomPlot 페인트 |
| `e2e_latency_ms` | 캡처 → 표시 요청 | 종단간 지연 |
| `e2e_full_ms` | 캡처 → 페인트 완료 | 페인트 포함 종단간 |
| `fg_fps` / `fg_sps` / `fg_spf` | — | 전경 처리 FPS/초당샘플/프레임당샘플 |
| `capture_gap_samples` | — | 캡처측 드롭 추정(`expected−written`) |

> 과부하 진단: **`proc2disp_latency_ms`**(처리 자체) + **`cap2proc_latency_ms`/`backlog_samples`**(밀린 정도)를 함께 본다.

## 7. 핵심 요약

- **버퍼 3종**: 입력 링 30초(스레드 전달) / 탭 버퍼 0.5~2.2초(라이브 렌더) / 이력 8분(되감기).
- **한 블록 ≤4096(≈85ms@48k)은 한 화면보다 짧다** → 누적 버퍼 필수. render는 `w`가 아니라 누적 `mBuf`를 그린다.
- **8분** = (15s+60s)×6자세 + 여유. **탭별 분리** = 긴 이력은 중앙 하나(메모리 중복 방지), 짧은 라이브는 탭마다(매 프레임 지연 방지).
- **과부하**: 일시 지연은 30초 링 + catch-up 루프로 흡수·회복. 지속 지연이면 GUI 프리징 → 30초 초과 시 **무음 오버런**(소비자측 감지 없음)으로 측정 붕괴.
- **계측**: 처리 시간 = `proc2disp_latency_ms`.
